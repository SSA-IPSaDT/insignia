## 🧭 Общие принципы разработки

1. **Строгая типизация — закон**: Любой публичный интерфейс, функция или компонент должны быть строго типизированы. Запрещено использовать `any` и намеренно подавлять ошибки компилятора (`@ts-ignore`) без веских оснований и согласования.
2. **Единый источник правды (SSOT)**: Типы API, схемы валидации и общие структуры данных обязаны находиться в пакете `packages/contracts`, а не дублироваться в `apps/web` или `apps/api`.
3. **Безопасность секретов**: Никаких открытых токенов, паролей и ключей в репозитории. Все чувствительные переменные шифруются с помощью **Fnox & Age**.
4. **Автоматизация проверок**: Код не должен отправляться в удаленный репозиторий без локального прохождения линтинга, форматирования и проверки типов.

## 🎨 Стандарты и форматирование кода

### Форматирование (Bun Formatter)

В проекте используется встроенный форматтер **Bun**, настройки которого зафиксированы в корневом файле `bunfig.toml`:

```toml
[fmt]
tabWidth = 4             # Отступ: 4 пробела
useTabs = false          # Использовать пробелы вместо табуляций
singleQuote = true       # Одинарные кавычки для строк
semi = true              # Точка с запятой в конце инструкций обязательна
sortImports = true       # Автоматическая сортировка импортов
sortTailwindcss = true   # Автоматическая сортировка CSS-классов Tailwind
```

#### Полезные команды:

```bash
# Проверить форматирование во всем проекте без изменения файлов
bun fmt --check

# Автоматически отформатировать весь проект
bun fmt
```

### Стандарты TypeScript

Мы используем современный строгий режим TypeScript (`strict: true`, `target: ESNext`, `verbatimModuleSyntax: true`):

1. **Явные типы импортов (`type-only imports`)**:
   Поскольку включен `verbatimModuleSyntax`, все сущности, используемые исключительно как типы, должны импортироваться со словом `type`:

    ```typescript
    // ❌ Неправильно:
    import { createUser, UserDto } from '@insignia/contracts';
    // ✅ Правильно:
    import { createUser, type UserDto } from '@insignia/contracts';
    // или
    import type { UserDto } from '@insignia/contracts';
    ```

2. **Запрет типа `any`**:
   Используйте `unknown` для динамических данных с последующей проверкой типов (type narrowing) или валидацией через схемы:

    ```typescript
    // ❌ Неправильно:
    function parsePayload(raw: any) {
        return raw.data;
    }

    // ✅ Правильно:
    function parsePayload(raw: unknown): PayloadData {
        if (isPayloadData(raw)) {
            return raw;
        }
        throw new Error('Invalid payload structure');
    }
    ```

3. **Безопасный доступ по индексам (`noUncheckedIndexedAccess: true`)**:
   TypeScript учитывает, что доступ по индексу массива или произвольному ключу объекта может вернуть `undefined`. Всегда выполняйте проверку на существование значения:

    ```typescript
    const firstItem = items[0];
    if (firstItem !== undefined) {
        // Безопасное использование
    }
    ```

4. **Явное указание возвращаемых типов для функций экспорта**:
   Для всех функций, экспортируемых из модулей, обязательно указывать тип возвращаемого значения для читаемости и оптимизации компиляции.

5. **Современный ECMAScript и стрелочные функции (`arrow functions`)**:
   Повсеместно используйте современный синтаксис ECMAScript. Для объявления функций отдавайте предпочтение **стрелочным функциям** (`const doSomething = (): void => { ... }`). Классический синтаксис ключевого слова `function` допускается только в тех редких случаях, когда он строго требуется языком (например, функции-генераторы `function*`).

### Соглашения об именовании

| Элемент                     | Соглашение                                                                | Пример                                  |
| :-------------------------- | :------------------------------------------------------------------------ | :-------------------------------------- |
| **Файлы утилит / сервисов** | `kebab-case`                                                              | `user-service.ts`, `auth-guard.ts`      |
| **Файлы компонентов**       | `PascalCase`                                                              | `UserProfile.svelte`, `Header.svelte`   |
| **Интерфейсы и типы**       | `PascalCase`                                                              | `UserProfile`, `CreateOrderRequest`     |
| **Перечисления (Enums)**    | `PascalCase` (значения в `UPPER_SNAKE_CASE` или `camelCase`)              | `UserRole.ADMIN`, `OrderStatus.Pending` |
| **Функции и методы**        | `camelCase`                                                               | `fetchUserData`, `calculateTotal`       |
| **Переменные и константы**  | `camelCase` (для локальных), `UPPER_SNAKE_CASE` (для глобальных констант) | `currentStatus`, `MAX_RETRY_COUNT`      |
| **Директории**              | `kebab-case`                                                              | `api-clients`, `order-history`          |

### Организация импортов

Благодаря флагу `sortImports = true` в `bunfig.toml`, импорты группируются и сортируются автоматически:

1. Встроенные модули платформы (`node:fs`, `node:path`).
2. Внешние библиотеки из `node_modules` (`svelte`, `zod`, `hono` и т.д.).
3. Внутренние пакеты монорепозитория (`@insignia/contracts`, `@insignia/database`).
4. Локальные относительные импорты (`./components`, `../utils`).

## 🏗 Архитектурные правила монорепозитория

1. **Однонаправленные зависимости**:
    - `apps/*` могут зависеть от `packages/*`.
    - `packages/*` **не могут** зависеть от `apps/*`.
    - Пакеты `packages/*` могут зависеть от других пакетов нижнего уровня (например, `packages/database` может использовать типы из `packages/contracts`), но циклические зависимости строго запрещены.
2. **Изоляция окружения**:
    - Код внутри `packages/contracts` должен быть чистым и независимым от платформы (не содержать привязок к DOM, серверным сокетам или файловой системе), чтобы одинаково легко выполняться в браузере, Node.js, Bun и веб-воркерах.
3. **Модульность приложений**:
    - Приложения `apps/api`, `apps/bot` и `apps/web` независимы друг от друга. Общение между ними происходит исключительно по сетевым протоколам (HTTP, WebSocket, RPC), а не через прямые импорты кода.

## 🌿 Правила работы с Git и коммитами

### Именование веток

Каждая новая задача разрабатывается в отдельной ветке, ответвленной от актуальной ветки `master`. Название ветки формируется по шаблону:

`<тип>/<краткое-описание-на-английском>` или `<тип>/<номер-задачи>-<описание>`

**Допустимые префиксы:**

- `feature/` — разработка новой функциональности (`feature/user-auth`, `feature/INS-42-telegram-webhook`).
- `bugfix/` или `fix/` — исправление ошибки (`bugfix/payment-race-condition`).
- `refactor/` — рефакторинг кода без изменения внешнего поведения (`refactor/contracts-dto`).
- `docs/` — добавление или изменение документации (`docs/onboarding-guide`).
- `infra/` или `chore/` — инфраструктура, CI, обновление тулчейна (`infra/docker-redis`, `chore/bump-deps`).
- `rfc/` или `proposal/` — межмодульные архитектурные предложения от контрибьюторов сервисов согласно [TEAM.md](TEAM.md) (`proposal/bot-webhook-proxy`).

### Формат коммитов (Conventional Commits)

Мы следуем стандарту [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```text
<тип>(<область>): <краткое описание в настоящем времени>

[необязательное подробное тело коммита]

[необязательный подвал с ссылкой на задачу: Closes #123]
```

**Типы коммитов:**

- `feat`: новая функциональность.
- `fix`: исправление бага.
- `docs`: изменения в документации.
- `refactor`: правки кода, не исправляющие баг и не добавляющие функционал.
- `perf`: изменения, направленные на увеличение производительности.
- `test`: добавление или исправление тестов.
- `chore`: обслуживание проекта, правка конфигураций, обновление зависимостей.
- `ci`: изменение пайплайнов непрерывной интеграции.

**Области (Scope) в монорепозитории:**

- `api` — изменения в `apps/api`
- `bot` — изменения в `apps/bot`
- `web` — изменения в `apps/web`
- `contracts` — изменения в `packages/contracts`
- `db` или `database` — изменения в `packages/database`
- `infra` — инфраструктурные настройки (`infra/`, Docker)
- `tooling` — инструменты монорепозитория (Mise, Moon, Bun, Fnox)

**Примеры хороших коммитов:**

- `feat(api): implement passwordless login via telegram`
- `fix(contracts): make optional phone field in user schema`
- `docs: update onboarding guide with age key creation instructions`
- `chore(tooling): bump bun version to 1.4.4 in mise.toml`

## 🚀 Процесс Pull Request (PR)

### Подготовка PR

1. Синхронизируйте вашу рабочую ветку с последней версией ветки `master`:
    ```bash
    git fetch origin
    git rebase origin/master
    ```
2. Убедитесь, что все автоматические проверки проходят локально:
    ```bash
    # Форматирование
    bun fmt --check

    # Проверка типов TypeScript во всем воркспейсе
    bun run typecheck
    ```
3. Отправьте ветку в удаленный репозиторий и откройте Pull Request на GitHub.

### Чеклист перед отправкой

- [ ] Название PR понятно отражает суть изменений и следует Conventional Commits.
- [ ] Описание PR заполнено в соответствии с шаблоном (`.github/PULL_REQUEST_TEMPLATE.md`).
- [ ] Указаны затронутые приложения и пакеты (`apps/*`, `packages/*`).
- [ ] Отсутствуют незашифрованные секреты и лишние временные файлы.
- [ ] Все тесты и проверка типов (`bun run typecheck`) завершаются успешно.

### Прохождение Code Review

1. Каждому PR требуется как минимум один аппрув (Code Review) от мейнтейнера проекта.
2. При наличии замечаний вносите исправления дополнительными коммитами в эту же ветку.
3. После получения аппрува и успешного прохождения всех CI-проверок PR сливается в `master` (обычно методом **Squash and Merge** для поддержания чистоты истории).
