# Регламент работы с Git (Git Workflow)

В проекте **Insignia** используется адаптированная модель **GitHub Flow** (с элементами Trunk-Based Development), оптимизированная для работы с монорепозиторием. Все изменения попадают в основную ветку через Pull Requests после автоматических проверок и ревью.

---

## 🌳 Ветки репозитория

### Основная ветка (`main`)

- **`main`** — единственная постоянная ветка проекта, содержащая стабильный, готовый к деплою код.
- Прямые коммиты (`git push origin main`) строго **запрещены**. Все изменения вливаются только через Pull Requests.
- Ветка `main` защищена правилами GitHub: для слияния требуется обязательное прохождение CI-пайплайна и как минимум одно одобрение (Code Review).

### Временные ветки задач (Topic Branches)

Для каждой новой задачи создается отдельная ветка от актуального состояния `main`:

```bash
git checkout main
git pull origin main
git checkout -b <тип-ветки>/<название-задачи>
```

#### Правила именования веток:

Имя ветки должно быть кратким, написанным латиницей в `kebab-case` и содержать смысловой префикс:

| Префикс                | Назначение                               | Пример                                              |
| :--------------------- | :--------------------------------------- | :-------------------------------------------------- |
| `feature/`             | Разработка новой функциональности        | `feature/telegram-auth`, `feature/user-dashboard`   |
| `bugfix/` (или `fix/`) | Исправление ошибок в логике или UI       | `bugfix/token-refresh-error`, `fix/navbar-overflow` |
| `refactor/`            | Рефакторинг кода без изменения логики    | `refactor/contracts-zod-schemas`                    |
| `perf/`                | Оптимизация производительности           | `perf/db-query-caching`                             |
| `docs/`                | Обновление или создание документации     | `docs/git-workflow-guide`                           |
| `infra/`               | Инфраструктура, Docker, CI/CD            | `infra/docker-compose-postgres`                     |
| `chore/`               | Обновление зависимостей, правка тулчейна | `chore/upgrade-bun-1-4`                             |

## 📝 Правила оформления коммитов (Conventional Commits)

Мы строго придерживаемся спецификации [Conventional Commits v1.0.0](https://www.conventionalcommits.org/ru/v1.0.0/). Сообщения коммитов используются для автоматической генерации changelog и понимания истории изменений в монорепозитории.

### Структура коммита:

```text
<type>(<scope>): <short description>

[optional body: detailed explanation of the change]

[optional footer: BREAKING CHANGE or issue reference, e.g. Closes #42]
```

### 1. Допустимые типы (`type`):

- `feat` — новая возможность для пользователя или API.
- `fix` — исправление дефекта.
- `docs` — изменения исключительно в документации или комментариях.
- `refactor` — переработка кода без исправления багов и добавления функционала.
- `perf` — оптимизация скорости работы или использования памяти.
- `test` — добавление или модификация тестов.
- `build` — изменения в системе сборки или внешних зависимостях.
- `ci` — правки файлов конфигурации CI/CD (.github/workflows).
- `chore` — регулярные рутинные задачи (форматирование, обновление конфигов).

### 2. Области действия (`scope`):

В условиях монорепозитория область коммита указывает на конкретный пакет или приложение:

- `api` — серверный сервис (`apps/api`).
- `bot` — бот автоматизации (`apps/bot`).
- `web` — фронтенд интерфейс (`apps/web`).
- `contracts` — общие контракты и DTO (`packages/contracts`).
- `db` — база данных, модели и миграции (`packages/database`).
- `tooling` — общие инструменты репозитория (`mise.toml`, `bunfig.toml`, `.moon`).
- `infra` — Docker и окружение (`infra/`).

### Примеры:

```bash
# Новая фича в бэкенде:
git commit -m "feat(api): implement rate limiter for authentication endpoints"

# Исправление в контрактах:
git commit -m "fix(contracts): make middleName field optional in UserProfile schema"

# Обновление документации:
git commit -m "docs: add onboarding guide for new team members"

# Изменение с мажорными несовместимыми изменениями (Breaking Change):
git commit -m "feat(api)!: migrate auth tokens from jwt to opaque bearer tokens

BREAKING CHANGE: all clients must update their auth header parsing logic."
```

## 🛡 Локальные хуки (Hk)

В репозитории используется **Hk** (`mise.toml`) для выполнения быстрых проверок перед созданием коммита и отправкой в репозиторий:

- **pre-commit**: проверяет корректность форматирования измененных файлов (`bun fmt --check`).
- **commit-msg**: валидирует синтаксис сообщения коммита по правилам Conventional Commits.
- **pre-push**: запускает проверку типов (`bun run typecheck`).

## 🔄 Жизненный цикл Pull Request (PR)

### 1. Синхронизация ветки

Перед отправкой ветки на проверку обновите ее от последнего `origin/main`:

```bash
git fetch origin main
git rebase origin/main
```

_(При возникновении конфликтов разрешите их локально и продолжите `git rebase --continue`)._

### 2. Локальная самопроверка

Перед созданием PR выполните:

```bash
bun fmt
bun run typecheck
```

### 3. Оформление Pull Request

- Заголовок PR должен соответствовать формату Conventional Commits.
- Описание оформляется по шаблону `.github/PULL_REQUEST_TEMPLATE.md`:
    - Краткое объяснение внесенных изменений;
    - Отметка затронутых проектов (`apps/*`, `packages/*`);
    - Заполнение чеклиста качества.

### 4. Code Review и правки

- Назначьте ревьюеров из числа мейнтейнеров затронутых компонентов.
- Если ревьюер оставил комментарии, вносите исправления дополнительными коммитами в эту же ветку.
- Не делайте force-push (`git push -f`) во время активного ревью, чтобы ревьюеры могли отслеживать разницу между версиями.

### 5. Слияние (Merge)

- Стратегия слияния по умолчанию: **Squash and Merge**.
- Сообщение сжатого коммита редактируется в лаконичный и понятный Conventional Commit, сохраняя чистую и линейную историю в ветке `main`.
- После слияния локальная и удаленная тематическая ветка удаляются.
