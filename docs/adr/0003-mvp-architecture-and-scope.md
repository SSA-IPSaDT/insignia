# [ADR-0003] Архитектура и границы функционала MVP платформы Insignia

- **Статус**: Принято
- **Дата**: 2026-11-02
- **Авторы**: naylour
- **Область (Scope)**: all (`apps/bot`, `apps/web`, `apps/api`, `packages/contracts`, `packages/database`)

---

## Контекст и проблематика

Платформа **Insignia** разрабатывается для автоматизации и контроля проведения мероприятий в вузе (Профком, Студенческое научное общество, Студсоветы институтов и кластеров, Совет молодых ученых и др.).

Ключевой сценарий платформы:

1. Организации создают мероприятия и настраивают формы сбора заявок (для обычных участников и для оргкомитета/волонтеров).
2. Студенты находят мероприятия, регистрируются и получают обратную связь.
3. Организаторы контролируют явку, учитывают волонтерские часы и выгружают отчеты.

В команде четко распределены роли:

- **`@naylour`** (Lead Architect / Fullstack): отвечает за инфраструктуру, базу данных (`packages/database`), серверное API (`apps/api`) и веб-интерфейс админки (`apps/web`).
- **`@segn1s`** (Bot Service Contributor): отвечает за сервис Telegram-бота (`apps/bot`) и осваивает TypeScript на практике.

Требуется зафиксировать технические границы **MVP (v0.1.0)**, архитектуру сквозного сценария (Vertical Slice) и распределение задач между сервисами, чтобы разработчики могли вести разработку параллельно без блокировок.

---

## Факторы принятия решения (Decision Drivers)

1. **Скорость выпуска первого сквозного сценария (Vertical Slice)**: минимальное время до первой рабочей связки _«Админка API <-> Бот <-> БД»_.
2. **Сбалансированная загрузка команды**: передача в `apps/bot` полноценного, изолированного и интересного функционала для контрибьютора бота.
3. **Оптимизация трудозатрат на фронтенд**: исключение необходимости верстки отдельного Telegram Mini App на этапе MVP.
4. **Современный UX в Telegram**: использование Telegram Rich Text (встраивание интерактивных кнопок прямо в текст сообщений) вместо громоздких клавиатур.
5. **Типобезопасность и единый источник контрактов**: синхронизация структур данных через `packages/contracts`.

---

## Рассмотренные варианты

### Вариант 1: Реализация прохождения форм только через Telegram Mini App (SvelteKit)

- **Плюсы**: Единая веб-кодовая база для форм и админки.
- **Минусы**: Перегружает ведущего разработчика (@naylour), оставляет разработчика бота (@segn1s) с минимальным набором задач (простая маршрутизация ссылок), увеличивает срок выхода MVP.

### Вариант 2: Гибридный запуск с опросом внутри чата бота на базе FSM (Выбранный вариант)

- **Плюсы**:
    - Бот берет на себя роль основного интерфейса взаимодействия со студентами через State Machine (FSM).
    - Веб-разработка концентрируется исключительно на административной панели для организаторов.
    - Разработчик бота получает самостоятельный фронтенд в Telegram с широким полем для практики в TypeScript.
    - Поддержка Telegram Rich Text и Inline Query делает продукт виральным и удобным без ожидания Mini App.
- **Минусы**: В будущем (v1.1+) потребуется перенести или продублировать интерфейс прохождения форм в Telegram Mini App.

---

## Принятое решение

Утвержден скоуп **MVP (v0.1.0)** со сквозным сценарием:
**Создание мероприятия и формы в админке -> Регистрация через чат-бота с Rich Text -> Сбор заявок в БД -> Уведомления и выгрузка отчетов.**

### 1. Сервис Telegram-бота (`apps/bot` — `@segn1s`)

- **Интерактивный FSM-опрос в чате**:
    - Точка входа: deeplink `/start form_<formId>`.
    - Пошаговый опрос по схеме полей формы.
    - Использование Telegram Rich Text: интерактивные элементы и выбор вариантов встраиваются непосредственно в текст сообщения.
    - Автоподстановка известных данных студента (если профиль уже заполнен).
    - Завершение: благодарность и выдача инвайт-ссылки в закрытый чат мероприятия.
- **Личный кабинет студента**:
    - Команда `/profile`: просмотр и редактирование данных (ФИО, институт, курс, группа, контакты).
    - Команда `/my_events`: список активных и завершенных заявок со статусами (Ожидает, Одобрено, Отклонено).
    - Команда `/my_hours`: учет накопленных волонтерских часов.
- **Inline Query (Поиск мероприятий в чатах)**:
    - Вызов: `@bot_username <запрос>` в любом диалоге.
    - Отдача превью-карточек открытых мероприятий с кнопкой быстрой регистрации.
- **Приемник системных уведомлений**:
    - Служебный вебхук/эндпоинт для отправки оповещений студентам по команде API.

### 2. Веб-клиент (`apps/web` — `@naylour`)

- **Административная панель организатора**:
    - Авторизация представителей студенческих организаций.
    - Управление списком мероприятий (создание, даты, постер, описание, параметры).
    - Конструктор форм сбора заявок (добавление вопросов, тип: участник/волонтер, ссылка на чат после прохождения).
    - Дашборд заявок (таблица ответов, фильтрация по статусам, смена статуса заявки).
    - Экспорт таблицы участников в CSV / Excel.

### 3. Серверный API (`apps/api` — `@naylour`)

- **Модули**:
    - `auth`: сессии и разграничение прав организаторов.
    - `organizations` & `events`: CRUD вузовских объединений и мероприятий.
    - `forms`: CRUD форм и выдача схемы формы боту (`GET /api/forms/:id`).
    - `submissions`: прием ответов (`POST /api/forms/:id/submit`), фильтрация и экспорт.
    - `students`: хранение профилей и волонтерских часов.
    - `bot-internal`: эндпоинты поиска для Inline Query и триггеры уведомлений.

### 4. Контракты (`packages/contracts`)

- Единые Zod-схемы для сущностей: `EventDto`, `FormFieldSchema`, `FormDefinitionDto`, `SubmitFormSchema`, `StudentProfileDto`, `NotificationPayloadSchema`.

### 5. База данных (`packages/database`)

- Схема Prisma: `Organization`, `User`, `Event`, `RegistrationForm`, `StudentProfile`, `FormSubmission`.

## Последствия и компромиссы

### Положительные последствия:

- Четкое разделение ответственности: разработчик бота может работать полностью автономно, используя мок-ответы по контрактам `@insignia/contracts`.
- Сокращение времени выхода MVP в 2 раза за счет отказа от сложного веб-интерфейса формы на первом этапе.
- Готовая архитектура для масштабирования в v1.1 (добавление Mini App, QR-чекина, генерации сертификатов).

### Риски и компромиссы:

- Реализация форм в Telegram Mini App откладывается на релиз v1.1.
- Разработчику бота потребуется аккуратно спроектировать FSM-машину для обработки прерываний диалога (например, если пользователь пишет постороннее сообщение посреди опроса).
