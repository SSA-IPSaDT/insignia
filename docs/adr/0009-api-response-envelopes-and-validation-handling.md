# [ADR-0009] Стандартизация конвертов API и глобальный обработчик ошибок в Elysia

- **Статус**: Принято
- **Дата**: 2026-11-08
- **Авторы**: @naylour
- **Область (Scope)**: packages/contracts | apps/api

---

## Контекст и проблематика

В распределенной системе с несколькими типами клиентов (клиентское приложение `apps/app`, административная панель `apps/admin`, Telegram-бот `apps/bot`, сторонние интеграторы SDK) предсказуемость формата сетевых ответов является ключевым фактором стабильности.

В процессе реализации базового API платформы Insignia на фреймворке Elysia были выявлены следующие проблемы:

1. **Неоднородность формата ответов**:
   Возврат голых данных в одних эндпоинтах (`{ id: '1', ... }`) и оберток в других приводит к усложнению клиентского кода, вынуждая писать кастомные проверки структуры ответа на каждый сетевой вызов.
2. **Непригодность стандартных сообщений валидации Elysia для UI/UX**:
   По умолчанию механизм валидации Elysia при ошибках входных данных формирует глубокое техническое дерево `issues` валидатора (Zod/TypeBox) с системными сообщениями на английском языке (например, `Expected string, received number`, `Invalid regex pattern`) и внутренними путями схемы.
    - Такой формат нельзя показывать конечному пользователю в веб-интерфейсе или Telegram-боте.
    - Фронтенд-формам для подсветки невалидных инпутов требуется плоская структура вида `поле -> понятный текст ошибки`.
3. **Особенности области видимости (Scoping) плагинов в Elysia**:
   В архитектуре Elysia обработчики ошибок (`onError`), объявленные в корневом экземпляре или в подключенных плагинах, по умолчанию изолированы текущим скоупом. При монтировании вложенных модулей и контроллеров через `.use(usersController)` ошибки, выброшенные во вложенных контроллерах, могут игнорировать локальные перехватчики, если плагин не зарегистрирован глобально через модификатор `.as('global')`.
4. **Хардкод текстов ошибок в бэкенд-сервисе**:
   Размещение текстов валидационных ошибок и кодов прямо в коде контроллеров или плагина API нарушает принцип единого источника правды: клиенты и SDK не имеют доступа к этим константам.

---

## Факторы принятия решения (Decision Drivers)

- **Единый сетевой контракт (Unified Response Envelopes)**: Любой ответ API должен иметь предсказуемую структуру верхнего уровня как при успехе, так и при ошибке.
- **Превосходный User Experience (UX)**: Ошибки валидации должны содержать ясные, человекочитаемые подсказки на русском языке, сформулированные в контрактах.
- **Поддержка валидации форм на клиенте (DX)**: Наличие плоского словаря `fields: Record<string, string>` для мгновенной привязки ошибок к полям ввода пользовательского интерфейса.
- **Глобальная изоляция и перехват (Fault Tolerance)**: Ни одна внутренняя ошибка сервера или ошибка парсинга JSON не должна утекать наружу в виде сырого стектрейса.
- **Соблюдение границ пакетов**: Все DTO ответов, коды ошибок и стандартные сообщения должны принадлежать `packages/contracts`, а не `apps/api`.

## Рассмотренные варианты

### Вариант 1: Использование стандартного вывода ошибок Elysia

- **Описание**: Оставить нативную обработку ошибок Elysia без изменений.
- **Плюсы**:
    - Нулевые затраты на реализацию.
- **Минусы**:
    - Нечитаемые англоязычные технические сообщения для пользователей.
    - Утечка внутренних деталей реализации схемы наружу.
    - Невозможность удобной подсветки полей формы на клиенте без сложного парсинга `issues`.

### Вариант 2: Локальная обработка ошибок в каждом контроллере

- **Описание**: Оборачивать каждый метод контроллера в `try / catch` и формировать кастомный JSON.
- **Плюсы**:
    - Точечный контроль над каждым маршрутом.
- **Минусы**:
    - Огромное дублирование бойлерплейт-кода.
    - Неизбежный человеческий фактор и пропуск ошибок в новых модулях.

### Вариант 3: Выделенный пакет контрактов ответов и глобальный плагин ошибок в Elysia

- **Описание**:
    - В `packages/contracts` создается независимый модуль `response/`:
        - `envelopes.ts`: `apiResponseSchema<T>()`, `apiErrorResponseSchema`.
        - `errors.ts`: перечисление `CommonErrorCode` и словарь локализованных текстов `COMMON_ERROR_MESSAGES`.
        - `validation.ts`: схема `validationErrorResponseSchema`, фабрика `createValidationErrorResponse` и дефолтные сообщения.
    - В `apps/api` реализуется `errorPlugin` с явным вызовом `.as('global')`.
    - Плагин перехватывает типы ошибок: `VALIDATION`, `NOT_FOUND`, `PARSE`, `INTERNAL_SERVER_ERROR` и форматирует их в каноничный `ApiErrorResponse` без единой захардкоженной строки.
- **Плюсы**:
    - 100% единообразие всех ответов платформы.
    - Полное покрытие всех дочерних контроллеров благодаря `.as('global')`.
    - Удобный для фронтенда и мобильных клиентов словарь `fields`.
    - Тексты ошибок определены в контрактах и доступны клиентам/SDK.
- **Минусы**:
    - Незначительное увеличение размера ответа из-за мета-конверта (`success`, `data`).

## Принятое решение

Принят **Вариант 3**.

### 1. Архитектура контрактов ответов (`packages/contracts/src/response/`)

Модуль вынесен в самостоятельный подпуть контрактов с экспортом `@insignia/contracts/response`.

1. **Конверт успешного ответа (`ApiResponse<T>`)**:
    ```typescript
    {
        success: true,
        data: T
    }
    ```
2. **Конверт ошибки (`ApiErrorResponse`)**:
    ```typescript
    {
        success: false,
        error: {
            code: CommonErrorCode,
            message: string,
            details?: unknown
        }
    }
    ```
3. **Специализированный ответ валидации (`ValidationErrorResponse`)**:
   Наследует `ApiErrorResponse`, устанавливая `code: CommonErrorCode.VALIDATION_ERROR`, и добавляет плоский словарь полей:
    ```typescript
    {
        success: false,
        error: {
            code: 'VALIDATION_ERROR',
            message: 'Проверьте правильность заполнения полей формы.',
            fields: {
                'firstName': 'Имя обязательно для заполнения и не должно превышать 64 символа.',
                'username': 'Юзернейм может содержать только латинские буквы, цифры и знак подчеркивания.'
            }
        }
    }
    ```

### 2. Реализация плагина ошибок в Elysia (`apps/api/src/plugins/error.plugin.ts`)

- Плагин регистрируется с `.as('global')`, что обеспечивает автоматическое распространение перехватчика на все поддеревья маршрутов (`/v1`, `/users`, `/accounts`, `/telegram` и т.д.).
- Логика извлечения ошибок валидации:
    - Итерируется по `error.all` валидатора.
    - Извлекает имя поля из пути `path` (или `schemaPath`).
    - Очищает префиксы пути (например, `/body/firstName` $\to$ `firstName`).
    - Формирует чистый объект `fields`.
- Маппинг стандартных кодов статусов:
    - `VALIDATION` $\to$ HTTP 422 Unprocessable Entity.
    - `PARSE` $\to$ HTTP 400 Bad Request.
    - `NOT_FOUND` $\to$ HTTP 404 Not Found.
    - Непредвиденные исключения $\to$ HTTP 500 Internal Server Error (с логированием через `@insignia/logger` и скрытием технического стектрейса от клиента).

## Последствия и компромиссы

### Положительные последствия:

- **Безупречный DX и UX**: Любой клиент платформы получает предсказуемый ответ и понятные локализованные сообщения об ошибках.
- **Упрощение клиентской логики**: Формы в `apps/app` (Mini App / PWA) могут напрямую передавать `error.fields` в компоненты отображения инпутов.
- **Архитектурная чистота**: Бэкенд `apps/api` не содержит хардкодных строк ошибок, а переиспользует единый источник правды из `@insignia/contracts/response`.
- **Надежность маршрутизации**: Глобальный скоуп `.as('global')` исключает риск появления маршрутов с «необработанными» падениями.

### Ограничения и компромиссы:

- Любой новый тип доменной ошибки (например, `INSUFFICIENT_FUNDS`, `USER_BLOCKED`) должен регистрироваться в перечислениях и словарях контрактов.

---

## План внедрения

1. **Шаг 1**: Реализовать схему `response/` в `packages/contracts` и настроить субпакетный экспорт в `package.json`.
2. **Шаг 2**: Реализовать `errorPlugin` с `.as('global')` в `apps/api/src/plugins/error.plugin.ts`.
3. **Шаг 3**: Подключить `errorPlugin` в корневое приложение Elysia.
4. **Шаг 4**: Покрыть юнит- и интеграционными тестами (`apps/api/tests/error.test.ts`, `packages/contracts/tests/response.test.ts`).
