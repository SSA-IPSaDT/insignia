# [ADR-0002] Выбор протокола межсервисного взаимодействия на локальном сервере (HTTP TCP vs UNIX Domain Sockets)

- **Статус**: Принято
- **Дата**: 2026-10-30
- **Авторы**: Gemini, Naylour
- **Область (Scope)**: infrastructure, apps/api, apps/bot, apps/web

---

## Контекст и проблематика

На начальном этапе развития платформы **Insignia** все ключевые серверные компоненты разворачиваются и функционируют на одной физической машине (или виртуальном сервере):

1. `apps/api`: бэкенд на базе **Bun** и **Elysia.js**.
2. `apps/web`: SSR-сервер фронтенда на базе **SvelteKit** (Node/Bun adapter).
3. `apps/bot`: сервис Telegram-бота на базе **Bun**.

Взаимодействие между `apps/web` (во время серверного рендеринга данных в `+page.server.ts`), `apps/bot` и `apps/api` происходит локально. Нет необходимости совершать запросы через внешние публичные домены и DNS.

Встает вопрос выбора оптимального канала межпроцессного взаимодействия (IPC / Inter-Process Communication) между сервисами:

- Использовать традиционный **HTTP поверх сетевого интерфейса петли (TCP Loopback / `127.0.0.1`)**.
- Или задействовать **UNIX Domain Sockets (UDS / файловые сокеты `unix:/tmp/api.sock`)**.

---

## Факторы принятия решения (Decision Drivers)

1. **Производительность и задержка (Latency)**: Минимизация накладных расходов на передачу пакетов между SSR SvelteKit, ботом и API.
2. **Безопасность и площадь атаки (Attack Surface)**: Изоляция внутренних сервисных ручек от несанкционированного доступа извне хоста.
3. **Удобство разработки и отладки (Developer Experience / DX)**: Простота тестирования локальных эндпоинтов через консольные утилиты (`curl`, `httpie`) и инструменты разработчика.
4. **Совместимость с рантаймами**: Бесшовная поддержка механизмов в Bun, SvelteKit и используемых HTTP-клиентах без специфических хаков.

---

## Рассмотренные варианты

### Вариант 1: Традиционный HTTP поверх TCP Loopback (`http://127.0.0.1:PORT`)

- **Описание**: API-сервер открывает TCP-порт на локальном интерфейсе `127.0.0.1` (например, `:3000`), к которому обращаются `apps/web` и `apps/bot`.
- **Плюсы**:
    - **Максимальная простота и очевидность**: Любой HTTP-клиент (fetch, ky, ofetch) из коробки умеет работать с URL вида `http://127.0.0.1:3000`.
    - **Идеальная отладка**: Разработчик может легко проверить ручку через `curl http://127.0.0.1:3000/api/...`, Swagger UI или Postman.
    - **Абсолютная переносимость**: Одинаково работает на Linux, macOS и Windows (WSL).
- **Минусы**:
    - Запросы проходят через локальный сетевой стек ядра Linux (TCP хэндшейки, буферы сокетов, заголовки пакетов), создавая небольшой, но лишний оверхед CPU при огромном потоке запросов.
    - Риск случайного биндинга на `0.0.0.0` вместо `127.0.0.1`, что может непреднамеренно открыть внутренний API в публичную сеть при отсутствии файрвола.

### Вариант 2: UNIX Domain Sockets (UDS) (`unix:/run/insignia/api.sock`)

- **Описание**: Elysia/Bun запускает сервер не на сетевом порту, а на локальном файловом сокете в файловой системе Linux (например, `/run/insignia/api.sock` или `/tmp/api.sock`).
- **Плюсы**:
    - **Максимальная производительность IPC**: Данные передаются напрямую через память ядра ОС без сетевого стека, контрольных сумм и фрагментации пакетов. Задержка минимально возможная.
    - **Безупречная безопасность**: Никаких открытых TCP-портов на хосте. Доступ к API регулируется стандартными правами доступа файловой системы Linux (POSIX permissions / `chmod 0660` для общей группы сервисов).
    - Невозможно случайно выставить внутренний API наружу.
- **Минусы**:
    - Сложнее локальная отладка: стандартный `fetch('http://...')` не умеет прозрачно ходить в UNIX-сокеты без передачи кастомного диспетчера агента (`undici.Agent({ socketPath })` в Node или специальных опций в Bun).
    - Необходимость управления файлом сокета: удаление «зависшего» `.sock` файла при аварийном падении процесса, настройка прав доступа (`chown`/`chmod`) в Docker/systemd.

## Принятое решение

Принято решение реализовать **гибридный адаптивный подход с базовым использованием HTTP TCP Loopback и архитектурной готовностью к переключению на UNIX Domain Sockets в продакшене**:

1. **В среде разработки (Local Development)**:
   Используется **HTTP поверх TCP Loopback (`http://127.0.0.1:3000`)**. Это гарантирует превосходный DX: мгновенная отладка, доступ к Swagger UI в браузере, отсутствие проблем с правами на файлы сокетов.

2. **Архитектурная абстракция транспорта**:
   `apps/api` конфигурируется так, чтобы способ запуска определялся переменными окружения:
    - Если задана переменная `API_SOCKET_PATH` (например, `/run/insignia/api.sock`) — сервер слушает UNIX Domain Socket.
    - Если задан `API_PORT` (по умолчанию `3000`) — сервер слушает `127.0.0.1:PORT`.

3. **В продакшен-окружении (Production на одной машине)**:
   При необходимости максимального секьюрити и снижения накладных расходов при росте трафика между SSR SvelteKit и Elysia переключение на UNIX Domain Sockets осуществляется изменением конфигурации окружения без переписывания бизнес-логики сервисов.

---

## Последствия и компромиссы

### Положительные последствия:

- Простая и быстрая локальная разработка без трения.
- Безопасная архитектура: внутренний API не требует открытия портов во внешнюю сеть.
- Возможность выжать максимум производительности из Bun IPC при развертывании в продакшене через UDS.

### Риски и их минимизация:

- **Разные клиенты для сокетов**: Вспомогательный клиент вызовов в `@insignia/contracts` или в `apps/web` должен инкапсулировать работу с транспортом (поддержка `socketPath` при наличии переменной окружения).
