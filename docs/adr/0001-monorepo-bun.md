# [ADR-0001] Выбор архитектуры монорепозитория на базе Bun и Moonrepo

- **Статус**: Принято
- **Дата**: 2026-10-29
- **Авторы**: Архитектурная команда Insignia
- **Область (Scope)**: all (весь проект)

---

## Контекст и проблематика

Проект **Insignia** включает в себя несколько тесно взаимодействующих компонентов:

1. `apps/api`: бэкенд сервер с бизнес-логикой и API.
2. `apps/bot`: сервис автоматизации и взаимодействия через мессенджеры.
3. `apps/web`: клиентский веб-интерфейс.
4. `packages/contracts`: разделяемые контракты, DTO и схемы валидации.
5. `packages/database`: модели данных, миграции и ORM-клиент.

При разделении таких компонентов по отдельным репозиториям (полирепозиторий / polyrepo) возникают следующие критические проблемы:

- **Рассинхронизация контрактов**: Изменение серверного API требует публикации отдельного npm-пакета, ожидания его сборки и последующего обновления версий во фронтенде и боте. Это замедляет разработку и приводит к ошибкам несовместимости в рантайме.
- **Оверхед на инфраструктуру**: Дублирование настроек линтеров, форматирования, CI/CD пайплайнов и конфигураций TypeScript в каждом репозитории.
- **Сложность атомарных изменений**: Задача, затрагивающая одновременно изменение модели БД, эндпоинта API и отображения в UI, размывается на 3–4 отдельных pull request в разных репозиториях.

Требуется выбрать структуру репозитория и систему сборки/пакетного менеджмента, способную обеспечить максимальную скорость и надежность работы команды.

---

## Факторы принятия решения (Decision Drivers)

1. **Скорость работы тулчейна**: Минимальное время установки зависимостей (`install`), сборки (`build`), проверки типов (`typecheck`) и запуска локального dev-окружения.
2. **Единый источник контрактов (Type Safety)**: Мгновенное распространение изменений типов из `packages/contracts` на все приложения без необходимости публикации в приватный реестр пакетов.
3. **Эффективный CI/CD**: Возможность определять затронутые проекты (Affected projects) и запускать проверки только для измененного кода, экономя время и ресурсы раннеров.
4. **Консистентность тулчейна**: Исключение расхождений версий компиляторов и рантаймов между локальными машинами инженеров и серверами сборки.

---

## Рассмотренные варианты

### Вариант 1: Полирепозиторий (Polyrepo) с npm/pnpm

- **Описание**: Каждый сервис и общая библиотека хранятся в собственном Git-репозитории. Общие библиотеки публикуются в закрытый npm registry (GitHub Packages / Verdaccio).
- **Плюсы**:
    - Полная независимость версионирования каждого отдельного сервиса.
    - Меньший размер каждого репозитория при клонировании.
- **Минусы**:
    - Высокий бюрократический оверхед при межсервисных изменениях.
    - Постоянный риск поломки контрактов из-за запаздывающих обновлений зависимостей.
    - Медленная обратная связь при интеграционном тестировании.

### Вариант 2: Монорепозиторий на базе pnpm + Turborepo

- **Описание**: Единый репозиторий с воркспейсами pnpm и оркестратором Turborepo на Node.js.
- **Плюсы**:
    - Зрелая, проверенная экосистема.
    - Хорошее кэширование задач сборки.
- **Минусы**:
    - Более медленная установка пакетов по сравнению с Bun.
    - Для запуска TypeScript требуется дополнительный слой транспиляции (tsx, ts-node или предварительный tsc/esbuild).
    - Сложнее организация легковесного форматирования без установки тяжеловесных зависимостей ESLint/Prettier.

### Вариант 3: Монорепозиторий на базе Bun и Moonrepo (Выбранный вариант)

- **Описание**: Единый репозиторий, использующий **Bun** в качестве быстрого рантайма, пакетного менеджера и форматтера, и **Moonrepo (Moon)** в качестве оркестратора задач и сборки. Дополняется **Mise** для фиксации версий окружения и **Fnox/Age** для безопасного хранения секретов.
- **Плюсы**:
    - **Колоссальный выигрыш в скорости**: Bun устанавливает зависимости в разы быстрее pnpm, мгновенно выполняет `.ts` скрипты и быстро форматирует код.
    - **Moonrepo**: Написан на Rust, нативно строит граф зависимостей между `apps/*` и `packages/*`, поддерживает точечный запуск affected-задач и кросс-проектное кэширование.
    - **Нулевая фрагментация типов**: Любое изменение в `packages/contracts` мгновенно отражается во всех приложениях монорепозитория через `bun run typecheck`.
    - **Удобство онбординга**: Новый разработчик выполняет `mise install && bun install` и получает готовое окружение со всеми бинарниками.
- **Минусы**:
    - Молодая экосистема Bun (хотя стабильность версий 1.4+ закрыла подавляющее большинство несовместимостей с экосистемой Node).

## Принятое решение

Мы приняли решение организовать разработку в виде **монорепозитория под управлением Bun и Moonrepo**.

Основные компоненты архитектурного стека:

- **Менеджер среды**: `mise` (`mise.toml`) как единый источник версий `bun`, `moon`, `age`, `fnox`, `hk`.
- **Рантайм и пакетный менеджер**: `bun` (`bunfig.toml`, `bun.lock`) — отвечает за воркспейсы, скорость установки зависимостей и форматирование кода.
- **Оркестратор монорепозитория**: `moon` (`.moon/workspace.yml`) — отвечает за запуск задач (`build`, `test`, `typecheck`), топологическую сортировку и кэширование.
- **Секреты**: `fnox` с асимметричным шифрованием `age` — зашифрованные секреты хранятся прямо в репозитории (`fnox.toml`, `fnox.*.toml`), исключая передачу незащищенных `.env` файлов.
- **Контракты**: `packages/contracts` используется как единственный источник типов запросов и ответов для всех приложений.

---

## Последствия и компромиссы

### Положительные последствия:

- Возможность атомарных коммитов: один Pull Request может содержать изменение схемы БД, обновление API и правки фронтенд-компонента.
- Полная типобезопасность сквозь весь стек — от БД до веб-интерфейса.
- Высочайшая скорость локальной разработки и прохождения CI.
- Безопасный GitOps для секретов без риска утечки ключей.

### Риски и их минимизация:

- **Несовместимость некоторых npm-пакетов с Bun**: В `mise.toml` зафиксирована актуальная версия Node.js (26.x), которая может служить фоллбэком при специфических требованиях внешних зависимостей.
- **Кривая обучения Moonrepo**: Процесс работы подробно описан в документации для разработчиков (`docs/onboarding.md`, `docs/git-workflow.md`, `README.md`).
