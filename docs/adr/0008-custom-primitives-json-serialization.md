# [ADR-0008] Протокол сериализации кастомных примитивов (Temporal и BigInt) в JSON

- **Статус**: Принято
- **Дата**: 2026-11-08
- **Авторы**: @naylour
- **Область (Scope)**: packages/sdk | apps/api | apps/web | apps/admin

---

## Контекст и проблематика

В архитектуре Insignia используются современные типы данных языка JavaScript/TypeScript и рантайма Bun:

1. **`BigInt`**: Применяется для 64-битных целых чисел (`int64` в PostgreSQL), в частности для Telegram User ID, Telegram Chat ID, а также потенциальных финансовых транзакций и точных балансов.
2. **`Temporal API` (TC39)**: В кодовой базе платформы принят стандарт отказа от устаревшего и подверженного ошибкам объекта `Date` в пользу типов `Temporal.PlainDate` (календарная дата без времени и часового пояса, например, дата рождения) и `Temporal.Instant` (точная метка времени во вселенной).

При этом сетевое взаимодействие между сервисами монорепозитория (`apps/api` $\leftrightarrow$ `apps/web`, `apps/admin`, `apps/bot`) и внешними клиентами SDK осуществляется по протоколу HTTP/REST с полезной нагрузкой в формате **JSON**.

Возникают фундаментальные технические ограничения спецификации JSON (RFC 8259):

- **Несовместимость с `BigInt`**: Вызов `JSON.stringify({ id: 1234567890123456789n })` в стандартном JavaScript завершается фатальной ошибкой `TypeError: Do not know how to serialize a BigInt`.
- **Потеря числовой точности (IEEE 754)**: Если преобразовывать `BigInt` в число `Number`, любые значения, превышающие `Number.MAX_SAFE_INTEGER` ($2^{53} - 1 \approx 9.007 \times 10^{15}$), необратимо искажаются в браузерах и JavaScript-клиентах (что регулярно происходит с идентификаторами Telegram).
- **Деградация семантики дат**: Стандартный объект `Date` всегда привязан к локальному времени или милисекундам с эпохи Unix, что приводит к «сдвигу» дат рождения пользователей на одни сутки назад/вперед в зависимости от часового пояса клиента.

## Факторы принятия решения (Decision Drivers)

- **Целостность данных без искажений**: Идентификаторы Telegram и финансовые значения никогда не должны терять точность при передаче по сети.
- **Стандартизация строкового протокола (Wire Format)**: Формат передачи должен оставаться чистым, валидным JSON, совместимым с любыми сторонними языками программирования (Go, Python, Swift, Kotlin).
- **Прозрачность для разработчика (Developer Experience)**: Внутри клиентского кода и бэкенда разработчик должен работать с полноценными объектами `BigInt` и `Temporal`, а не заниматься ручным преобразованием строк на каждом уровне.
- **Совместимость с SSR в SvelteKit**: Серверный и клиентский рендеринг в `apps/web` и `apps/admin` должны корректно передавать эти типы через гидратацию страниц.

## Рассмотренные варианты

### Вариант 1: Использование сторонних протоколов сериализации (`superjson` или `devalue`)

- **Описание**: Передавать данные с мета-тегами типов через специализированные библиотеки сериализации.
- **Плюсы**:
    - Автоматическое восстановление типов «из коробки».
- **Минусы**:
    - Ломает стандартный REST API: сторонние интеграторы и клиенты не смогут читать формат без специализированных парсеров.
    - Увеличивает размер полезной нагрузки и накладывает жесткую зависимость на библиотеки.
    - Противоречит ADR-0006 о минимализме публичного SDK (только `ky`).

### Вариант 2: Передача `BigInt` как `number`, а дат — как Unix timestamp в миллисекундах

- **Описание**: Использовать стандартные числовые типы JSON.
- **Плюсы**:
    - Нативно поддерживается JSON.
- **Минусы**:
    - Фатальная потеря разрядов в числах $> 2^{53} - 1$ в JS-клиентах.
    - Потеря различия между датой без времени (`PlainDate`) и моментом времени (`Instant`).

### Вариант 3: Каноничный строковый Wire-формат с парсером/reviver в SDK и Zod-трансформерами

- **Описание**:
    - В сетевом слое (wire):
        - `BigInt` сериализуется как десятичная строка (`"123456789012345678"`).
        - `Temporal.PlainDate` сериализуется по стандарту ISO-8601 даты: `YYYY-MM-DD` (`"2000-01-15"`).
        - `Temporal.Instant` сериализуется по стандарту ISO-8601 времени UTC: `YYYY-MM-DDTHH:mm:ss.sssZ`.
    - На бэкенде (`apps/api`): Zod-схемы валидируют строковые форматы и при необходимости трансформируют их в примитивы, либо контроллеры сериализуют их через кастомный `JSON.stringify` replacer.
    - В SDK (`packages/sdk`): сетевой клиент использует кастомный `reviver` / функцию десериализации `parseInsigniaJson`, восстанавливающую `BigInt` и `Temporal` по строгим регулярным выражениям или схемам контрактов.
    - В SvelteKit (`apps/web`, `apps/admin`): хуки `transport` для бесшовной сериализации между сервером и браузером.
- **Плюсы**:
    - 100% валидный стандартный JSON, понятный любому внешнему клиенту и Scalar/OpenAPI.
    - Нулевая потеря точности `BigInt`.
    - Корректная семантика дат без искажений часовых поясов.
    - Соответствие архитектурным ограничениям публичного SDK.
- **Минусы**:
    - Необходимость регистрации кастомных десериализаторов в клиентах.

## Принятое решение

Принят **Вариант 3**.

### 1. Канонические правила Wire-формата

1. **Большие целые числа (`BigInt`)**:
    - Передаются в JSON как строки из цифр: `z.string().regex(/^-?\d+$/)` или трансформер `z.coerce.bigint()` / `z.bigint()`.
    - Пример: `"telegramId": "98765432101234567"`.
2. **Календарные даты (`Temporal.PlainDate`)**:
    - Передаются строго в формате `YYYY-MM-DD`.
    - Регулярное выражение: `/^\d{4}-(?:0[1-9]|1[0-2])-(?:0[1-9]|[12]\d|3[01])$/`.
    - Пример: `"birthDate": "2002-04-12"`.
3. **Моменты времени (`Temporal.Instant`)**:
    - Передаются в формате ISO-8601 с суффиксом `Z` (UTC).
    - Пример: `"createdAt": "2026-11-08T14:30:00.000Z"`.

### 2. Слой API (`apps/api`)

- Для ответов Elysia реализуется кастомная сериализация BigInt (через `BigInt.prototype.toJSON = function() { return this.toString(); }` или явный сериализатор эндпоинтов).
- Схемы контрактов (`packages/contracts`) валидируют входящие данные: `z.bigint()` либо строковые представления с проверками диапазона и положительности (`> 0n`).

### 3. Слой клиентского SDK (`packages/sdk`)

- В SDK внедряется десериализатор `parseInsigniaJson`, используемый по умолчанию в хуках ответа `ky` (`afterResponse`).
- Внешние потребители получают типизированные объекты `bigint` и даты без необходимости ручного парсинга.

### 4. Слой веб-приложений (`apps/web`, `apps/admin`)

- В SvelteKit настраивается механизм `transport` в `src/hooks.ts` / `src/hooks.server.ts` для поддержки передачи `BigInt` и `Temporal` данных при SSR-загрузке страниц (`PageData`).

## Последствия и компромиссы

### Положительные последствия:

- **Абсолютная безопасность и надежность идентификаторов**: Исключена возможность перепутать или обрезать Telegram ID пользователей.
- **Чистый публичный API**: Документация OpenAPI/Scalar четко описывает типы (`string` с форматом `date` или `int64`).
- **Будущеустойчивость**: Платформа готова к полноценному переходу браузеров на встроенный стандарт `Temporal`.

### Ограничения и компромиссы:

- Необходимость подключения полифила `@js-temporal/polyfill` в средах, где нативный `Temporal` еще не включен по умолчанию.
