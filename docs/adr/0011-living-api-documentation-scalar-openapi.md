# [ADR-0011] Живая интерактивная документация API через Scalar и OpenAPI 3.1.2

- **Статус**: Принято
- **Дата**: 2026-11-08
- **Авторы**: @naylour, Antigravity (AI Assistant)
- **Область (Scope)**: apps/api | packages/contracts

---

## Контекст и проблематика

Документация программных интерфейсов (API) является критически важным артефактом командной разработки, синхронизирующим работу инженеров бэкенда (`apps/api`), клиентского приложения (`apps/app`), административной панели (`apps/admin`), Telegram-бота (`apps/bot`) и сторонних потребителей клиентского SDK.

В традиционном процессе разработки документация часто страдает от следующих фундаментальных проблем:

1. **Рассинхронизация с кодовой базой (Documentation Rot)**:
   При ручном ведении спецификаций (Swagger YAML, Markdown-файлы, Postman-коллекции) документация устаревает уже в момент внесения первого изменения в эндпоинт или контракт.
2. **Устаревший стек отображения (Swagger UI)**:
   Традиционный инструмент Swagger UI морально и технически устарел: он имеет неудовлетворительную поддержку стандарта OpenAPI 3.1.x, плохую читаемость сложных вложенных схем, тяжеловесный бандл и неадаптивный пользовательский интерфейс для мобильных устройств.
3. **Анонимизация схем и неинформативность автогенерации в Elysia**:
   При автоматической генерации спецификации OpenAPI из Zod-схем во фреймворке Elysia без явной конфигурации возникают системные проблемы:
    - Схемы регистрируются как анонимные инлайн-объекты или получают автогенерированные имена вида `InlineModel_1`, засоряя спецификацию.
    - Поля моделей лишены текстовых описаний, оставляя разработчика в неведении относительно бизнес-смысла атрибутов.
    - Маршруты группируются хаотично без иерархической структуры тегов.

---

## Факторы принятия решения (Decision Drivers)

- **Концепция «Живой документации» (Living Documentation)**: Документация должна быть 100% производной от реального исполняемого кода и Zod-контрактов (`Single Source of Truth`).
- **Современный интерактивный интерфейс (Scalar)**: Использование передового инструмента с поддержкой OpenAPI 3.1.2, встроенным интерактивным HTTP-клиентом для тестирования запросов, поддержкой светлой/темной тем и генерацией кода на десятках языков программирования.
- **Информативность и культура контрактов (DX)**: Каждая публичная модель, поле и маршрут должны содержать исчерпывающие описания на русском языке.
- **Поддержка переиспользуемых компонентов (`components.schemas`)**: Центральные DTO, конверты ответов и коды ошибок должны регистрироваться как именованные схемы в спецификации.

## Рассмотренные варианты

### Вариант 1: Традиционный Swagger UI (`@elysiajs/swagger`)

- **Описание**: Стандартный плагин Swagger UI для Elysia.
- **Плюсы**:
    - Привычный, многолетний интерфейс.
- **Минусы**:
    - Устаревший дизайн.
    - Проблемы с рендерингом схем OpenAPI 3.1 (`anyOf`, `oneOf`, расширенные типы `null`).
    - Низкая скорость работы и слабая эргономика поиска.

### Вариант 2: Внешние облачные платформы (Readme.com, GitBook, Postman)

- **Описание**: Экспорт спецификации во внешние платные или облачные сервисы.
- **Плюсы**:
    - Богатые возможности хостинга статей.
- **Минусы**:
    - Зависимость от сторонней облачной инфраструктуры.
    - Разрыв локального контура разработки (невозможно тестировать API локально без интернета).
    - Сложности с синхронизацией приватных веток.

### Вариант 3: Интеграция Scalar API Reference с OpenAPI 3.1.2 и регистрацией моделей контрактов

- **Описание**:
    - Подключение современного движка документации **Scalar** через `@scalar/elysiajs` или кастомный плагин OpenAPI.
    - Явная регистрация контрактов в `app.model({ ... })` плагина `docs.plugin.ts` для наполнения секции `components.schemas`.
    - Добавление человекочитаемых описаний ко всем схемам и полям через `.describe('...')` библиотеки Zod.
    - Структурированная иерархия тегов с префиксами и описаниями на русском языке.
- **Плюсы**:
    - Превосходный современный интерфейс с быстрым поиском и встроенным API-клиентом.
    - Полная поддержка стандартов OpenAPI 3.1.2.
    - Чистый файл спецификации `/docs/json` с именованными компонентами.
    - Документация всегда синхронна с кодом бэкенда.
- **Минусы**:
    - Необходимость дисциплины команды по добавлению вызовов `.describe()` к новым Zod-схемам.

## Принятое решение

Принят **Вариант 3**.

### 1. Архитектура плагина документации (`apps/api/src/plugins/docs.plugin.ts`)

1. **Подключение Scalar API Reference**:
   Документация доступна локально и в средах развертывания по адресу `/docs`, а машиночитаемая спецификация OpenAPI 3.1.2 доступна по адресу `/docs/json`.
2. **Регистрация компонентов (`components.schemas`)**:
   В `docs.plugin.ts` через метод `app.model()` зарегистрированы фундаментальные схемы платформы:
    - `CommonErrorCode`: перечисление кодов ошибок.
    - `ApiSuccessResponse`: универсальный конверт успеха.
    - `ApiErrorResponse`: каноничный конверт ошибки.
    - `ValidationErrorResponse`: конверт ошибки валидации с картой полей `fields`.
    - `UserBase`, `TelegramAccountBase`: базовые схемы доменных сущностей.
    - `HealthCheck`: схемы проверки состояния сервиса.
3. **Таксономия и иерархия тегов**:
   Маршруты организуются по структурированным тегам:
    - `System` — системные служебные эндпоинты (healthcheck, метрики).
    - `Users` — операции над пользователями платформы.
    - `Users: Accounts` — подключенные аккаунты и внешние сервисы.
    - `Users: Telegram` — операции синхронизации и аутентификации через Telegram.
    - `Auth` — токены и сессии.

### 2. Стандарт самодокументируемых контрактов (`packages/contracts`)

Все схемы в `packages/contracts` обязаны снабжаться вызовами `.describe()`:

- На уровне всей схемы: `.describe('Базовая схема профиля пользователя платформы Insignia')`.
- На уровне каждого отдельного поля:
    ```typescript
    firstName: z.string()
        .min(1, 'Имя обязательно для заполнения')
        .max(64, 'Имя не должно превышать 64 символа')
        .describe('Имя пользователя (от 1 до 64 символов)'),
    ```

## Последствия и компромиссы

### Положительные последствия:

- **Идеальный Developer Experience (DX)**: Любой разработчик команды видит актуальную интерактивную документацию сразу после запуска `bun run dev`.
- **Автоматическая генерация клиентов**: Спецификация `/docs/json` валидна по стандарту OpenAPI 3.1.2 и может использоваться генераторами кода (OpenAPI Generator, Orval, hey-api).
- **Снижение порога входа (Onboarding)**: Новые контрибьюторы могут исследовать архитектуру данных и API через браузер без чтения исходного кода.

### Ограничения и компромиссы:

- Разработчики обязаны помнить о вызовах `.describe()` при создании новых полей и моделей.

---

## План внедрения

1. **Шаг 1**: Реализовать `docsPlugin` с поддержкой Scalar и регистрацией моделей в `apps/api/src/plugins/docs.plugin.ts`.
2. **Шаг 2**: Добавить `.describe()` ко всем схемам `packages/contracts/src/response/` и `packages/contracts/src/users/`.
3. **Шаг 3**: Настроить теги и метаданные эндпоинтов в контроллерах `apps/api/src/modules/`.
4. **Шаг 4**: Проверить генерацию OpenAPI спецификации на эндпоинте `GET /docs/json`.
