# [ADR-0006] Стратегия упаковки публичного SDK и инлайнинга типов контрактов

- **Статус**: Принято
- **Дата**: 2026-11-08

- **Область (Scope)**: packages/sdk | packages/contracts | tooling

## Контекст и проблематика

Решение сформировано в процессе совместного парного проектирования и анализа вариантов упаковки между ведущим разработчиком (@naylour) и AI-ассистентом Antigravity в рамках задачи по созданию клиентского SDK платформы.

Клиентский изоморфный SDK платформы Insignia (`packages/sdk`, `@insignia/sdk`) на текущем этапе обеспечивает взаимодействие внутренних сервисов (`apps/admin`, `apps/web`) с бэкендом `apps/api`. Однако в стратегическом плане развития платформы заложена возможность **публичного распространения SDK** (публикация в npm / предоставление внешним разработчикам для интеграции с API платформы Insignia по публичной документации).

При переходе SDK в статус публичной библиотеки возникают следующие архитектурные вызовы:

1. **Разделение ответственности и Single Source of Truth**:
   Пакет `packages/contracts` является единым источником правды для схем валидации (Zod) и типов DTO платформы. SDK (`packages/sdk`) должен реализовывать сетевую логику на основе контрактов, не дублируя вручную типы запросов и ответов в своем исходном коде (`packages/sdk/src`).
2. **Проблема внешних импортов в декларациях типов (`.d.ts`)**:
   Стандартный компилятор `tsc` при генерации `.d.ts` сохраняет ссылки на локальные пакеты монорепозитория (`import type { HealthDTO } from '@insignia/contracts/health'`). При установке внешним пользователем из npm пакет `@insignia/contracts` отсутствует в его окружении, что приводит к ошибкам компиляции TypeScript: `Cannot find module '@insignia/contracts'`.
3. **Изоляция от рантайма и типов валидатора (Zod)**:
   Вся валидация сетевого ввода/вывода в Insignia выполняется на стороне API. Клиентскому SDK не требуются схемы Zod в рантайме. Более того, потребитель SDK не должен быть обязан устанавливать `zod` в свои `dependencies` или `devDependencies` ради типов.
4. **Минималистичный состав зависимостей**:
   SDK должен быть максимально легковесным и компактным. Единственной внешней зависимостью пакета в рантайме должна быть библиотека **`ky`**.

---

## Факторы принятия решения (Decision Drivers)

- **Полная автономность публичного пакета**: Внешний разработчик устанавливает `@insignia/sdk` как обычную npm-зависимость без необходимости доступа к репозиторию или пакетам монорепозитория (`@insignia/contracts`).
- **Единственная рантайм-зависимость — `ky`**: Нулевой лишний вес в браузере и на сервере, исключение Zod из клиентского бандла и из `node_modules` потребителя.
- **Чистота типов в `dist/*.d.ts`**: Все DTO и типы ответов (`ApiResponse`, `ApiErrorResponse`, `HealthDTO`, `UserDTO`) должны быть представлены как чистые TypeScript-типы без ссылок на `z.infer` и внутренние модули монорепозитория.
- **Сохранение архитектурной чистоты в `src`**: Исходный код SDK не должен содержать дублирующего ручного копирования типов из контрактов.

## Рассмотренные варианты

### Вариант 1: Публикация `@insignia/contracts` в качестве внешней зависимости SDK

- **Описание**: Опубликовать `@insignia/contracts` в npm и добавить его в `dependencies` пакета `@insignia/sdk`.
- **Плюсы**:
    - `tsc` без изменений может ссылаться на `@insignia/contracts`.
- **Минусы**:
    - Раскрывает внутренние схемы валидации Zod и логику сервера.
    - Принуждает внешнего потребителя ставить зависимость `zod`, раздувая `node_modules`.
    - Усложняет релизный цикл (необходимость синхронной публикации двух пакетов).

### Вариант 2: Ручное дублирование типов в `packages/sdk/src/types.ts`

- **Описание**: Вручную объявить интерфейсы DTO внутри SDK, разорвав зависимость от `@insignia/contracts`.
- **Плюсы**:
    - Автономность `dist/*.d.ts` «из коробки».
- **Минусы**:
    - Грубое нарушение принципа DRY и единого источника правды: при любом изменении контракта в `packages/contracts` разработчику придется вручную синхронизировать типы в SDK.
    - Риск рассинхронизации контрактов и клиентского SDK при командной разработке.

### Вариант 3: Использование `tsup` с резолвингом типов (`--dts-resolve`)

- **Описание**: Использование современного сборщика `tsup` на базе `esbuild` и `rollup-plugin-dts` с включением флага `--dts-resolve`. В этом режиме сборщик бандлит декларации в единый файл `dist/index.d.ts` и автоматически вытягивает (инлайнит) типы из зависимостей, помеченных для резолвинга, преобразуя их в самодостаточные определения.
- **Плюсы**:
    - Отраслевой стандарт для современных публичных библиотек и SDK.
    - Генерирует один компактный, самодостаточный файл типов `index.d.ts`.
    - Исходный код SDK остается чистым и импортирует контракты как положено.
- **Минусы / Текущие ограничения экосистемы**:
    - Инструмент `rollup-plugin-dts`, лежащий в основе `tsup`, исторически завязан на устаревший JavaScript Compiler API TypeScript. В текущем окружении монорепозитория (**TypeScript 7.0.2**) Compiler API был упразднен, что требует подключения слоя совместимости `@typescript/typescript6` либо переходного шага постобработки в `build.ts`.

### Вариант 4: Автоматический Post-build Inliner типов в `build.ts`

- **Описание**: Выполнение стандартной генерации деклараций через `tsc`, после чего скрипт сборки [build.ts](file:///home/naylour/Work/insignia/packages/sdk/build.ts) автоматически заменяет импорты `@insignia/contracts` на заинлайненные чистые типы в файлах `dist/`.
- **Плюсы**:
    - Полная независимость от сторонних бандлеров деклараций и капризов Compiler API.
    - Работает на любой версии TypeScript и в рантайме Bun.
- **Минусы**:
    - Требуется поддержка собственного скрипта преобразования при расширении набора экспортируемых DTO.

## Принятое решение

1. **Целевая модель SDK**:
    - Пакет `@insignia/sdk` проектируется и поддерживается как **потенциально публичная библиотека**.
    - **Единственная допустимая зависимость** в `dependencies` пакета `@insignia/sdk` — это библиотека **`ky`**.
    - Пакет `zod` **строго запрещен** в качестве рантайм- или внешней peer-зависимости SDK.
2. **Встраивание типов через `tsup` как целевая стратегия**:
    - Зафиксирована идея использовать `tsup` с флагом `--dts-resolve` для упаковки типов публичного SDK.
    - Сборщик `tsup` на этапе сборки вытягивает необходимые типы из `@insignia/contracts` и запекает их в результирующие `.d.ts`-файлы без сохранения ссылок на контракты и Zod.
3. **Переходный этап (совместимость с TypeScript 7)**:
    - Ввиду отсутствия JS Compiler API в TypeScript 7.0, сборка деклараций SDK временно обеспечивается связкой `tsc -p tsconfig.build.json` с последующим инлайнингом через `build.ts` либо установкой `@typescript/typescript6` для нужд `tsup`.
4. **Контракты как источник правды**:
    - Внутри кодовой базы `packages/sdk/src` разработчики продолжают импортировать типы строго из `@insignia/contracts` (`import type { ... } from '@insignia/contracts'`). Запрещено создавать дублирующие локальные типы в коде SDK.

---

## Последствия и компромиссы

### Положительные последствия:

- **Готовность к публичному релизу**: SDK может быть опубликован в реестр npm в любой момент без риска сломать типы у внешних пользователей.
- **Минимальный размер пакета**: Клиентский бандл содержит только сетевой слой на базе `ky` и методы модулей; размер бандла исчисляется килобайтами.
- **Соблюдение архитектурных границ**: Сохраняется жесткое разделение обязанностей между контрактами, бэкендом и клиентским кодом.

### Ограничения и риски:

- Необходимость контроля процесса сборки типов при обновлении тулчейна (переход между версиями TypeScript и бандлеров деклараций).
