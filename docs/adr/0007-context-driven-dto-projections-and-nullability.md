# [ADR-0007] Контекстно-ориентированные DTO-проекции и семантика nullability в REST API

- **Область (Scope)**: packages/contracts | apps/api | apps/web | apps/bot

## Контекст и проблематика

В архитектуре платформы Insignia модели базы данных (Prisma 8) содержат полный набор полей сущностей, включая системные временные метки (`createdAt`, `updatedAt`, `deletedAt`), служебные идентификаторы, роли доступа и чувствительные данные профиля пользователя.

В ходе проектирования первого вертикального среза функциональности пользователей (`User` и связанные аккаунты `TelegramAccount`) возникла необходимость определить стандарты:

1. **Изоляция ORM-моделей от сетевого контракта (Over-fetching & Information Leakage)**:
   Возврат ORM-сущности целиком клиенту недопустим: это приводит к утечке приватных данных (например, служебных флагов, внутренних заметок или полей модерации) и многократному перерасходу сетевого трафика.
2. **Контекст отображения данных**:
   Одной и той же сущности `User` в системе соответствуют принципиально разные сценарии использования:
    - _Публичный срез_: просмотр профиля другими пользователями (минимальный набор: идентификатор, имя, юзернейм, аватар).
    - _Приватный срез_: просмотр собственного профиля авторизованным пользователем (доступны дата рождения, роли, системные параметры).
    - _Административный срез_: аудит, статусы блокировок, полная история изменений.
3. **Семантическая дилемма `null` vs `undefined` в JSON REST API**:
    - В PostgreSQL и Prisma опциональные поля хранятся как `NULL`.
    - В JSON передача `null` для пустых полей (`"middleName": null`, `"avatarUrl": null`, `"updatedAt": null`) приводит к неоправданному росту размера полезной нагрузки (payload bloat), особенно в списках и коллекциях сущностей.
    - В операциях чтения (GET) отсутствие значения концептуально эквивалентно отсутствию свойства (`undefined` в JavaScript/TypeScript), что позволяет парсерам и сети экономить ресурсы.
    - В операциях частичного обновления (PATCH) существует критическое смысловое различие:
        - Ключ **опущен (`undefined`)**: свойство **не должно изменяться**.
        - Значение передано как **`null`**: значение поля в базе данных **должно быть очищено (сброшено в NULL)**.
        - Передано **непустое значение**: поле должно быть обновлено.

## Факторы принятия решения (Decision Drivers)

- **Безопасность и защита данных (Zero Data Leakage)**: Гарантия того, что приватные атрибуты пользователя никогда случайно не попадут в публичные эндпоинты.
- **Оптимизация сетевого трафика и размера payload**: Исключение передачи бесполезных `null`-полей при запросах чтения списков и деталей.
- **Однозначная семантика мутаций (PATCH)**: Четкое разграничение намерения «не трогать поле» (`undefined`) от намерения «стереть значение» (`null`).
- **Единый источник правил валидации полей (DRY)**: Базовые ограничения атрибутов (длины строк, регулярные выражения, понятные тексты ошибок) должны объявляться однократно и переиспользоваться во всех контекстных DTO.

## Рассмотренные варианты

### Вариант 1: Использование единого DTO на основе Prisma-модели с сохранением всех `null`

- **Описание**: Генерировать единый `UserDto` прямо из Prisma и возвращать все поля, сериализуя отсутствующие значения как `null`.
- **Плюсы**:
    - Быстрота начальной разработки, минимум ручного кода.
- **Минусы**:
    - Катастрофическая утечка служебных полей в публичный API.
    - Избыточный размер JSON-ответов.
    - Невозможность гибко скрыть отдельные поля для чужих профилей.

### Вариант 2: Запрет `null` на сетевом уровне, использование пустых строк и фиктивных значений

- **Описание**: Все опциональные поля преобразовывать в пустые строки `""` или `0`.
- **Плюсы**:
    - Отсутствие `null` в типах.
- **Минусы**:
    - Ломает семантику баз данных (потеря `NULL`, конфликты уникальных индексов `UNIQUE`).
    - Невозможно отличить действительно пустое имя от не введенного значения.

### Вариант 3: Контекстно-ориентированные DTO с иерархией схем и строгим разделением семантики `null`/`undefined`

- **Описание**:
    1. Выделение атомарных определений полей в `userFields` (`user.base.ts`).
    2. Формирование специализированных DTO-проекций: `PublicUserDto`, `UserProfileDto`, `UpdateUserDto`.
    3. В схемах чтения (GET) опциональные поля объявляются как `.optional()` (опускаются при сериализации, если они не заданы).
    4. В схемах обновления (PATCH) поля объявляются как `.nullable().optional()`.
    5. В базе данных сохраняется каноничный `NULL`.
- **Плюсы**:
    - Идеальная безопасность: каждый эндпоинт отдает ровно те поля, которые разрешены для данного контекста.
    - Экономия сетевого трафика: пустые поля просто отсутствуют в ответе.
    - Точная семантика частичного обновления.
    - Переиспользование проверок и локализованных сообщений об ошибках из базового словаря полей.
- **Минусы**:
    - Необходимость явного маппинга или выбора (`select`) полей в репозиториях/сервисах.

## Принятое решение

Принят **Вариант 3**.

### 1. Архитектура контрактов пользователя (`packages/contracts/src/users/`)

1. **Атомарные поля (`base.ts`)**:
   Все правила валидации конкретных полей (типы, длины от 1 до 64 символов, regex для `username`, читаемые сообщения об ошибках) объявляются в словаре `userFields`.
2. **Контекстные проекции**:
    - **`PublicUserDto`**: Минимальная публичная проекция (`id`, `firstName`, `username`, `avatarUrl`). Не содержит приватных данных.
    - **`UserProfileDto`**: Полная проекция текущего авторизованного пользователя (`id`, `firstName`, `lastName`, `middleName`, `username`, `birthDate`, `role`, `status`, `createdAt`, `updatedAt`).
    - **`UpdateUserDto`**: Схема мутации для `PATCH /v1/users/me`, где поля типизированы как `.nullable().optional()`.

### 2. Семантика сериализации `null` vs `undefined`

- **Для GET-ответов**:
  При сериализации ответа в API поля со значением `null` или `undefined` исключаются из результирующего JSON-объекта (или типизируются как опциональные ключи `?: string`), сокращая объем передаваемых байт.
- **Для PATCH-запросов**:
    - `{ "lastName": "Иванов" }` $\to$ обновить фамилию.
    - `{ "lastName": null }` $\to$ удалить фамилию (записать `NULL` в БД).
    - `{}` (ключ отсутствует) $\to$ оставить существующее значение без изменений.
- **Для базы данных**:
  В слое постоянства (`packages/database`) отсутствие значения всегда хранится строго как SQL `NULL`.

## Последствия и компромиссы

### Положительные последствия:

- **Полная защита от утечек данных**: Клиент никогда не получит доступ к не предназначенным ему полям.
- **Экономия пропускной способности сети**: JSON-ответы компактны и лишены информационного мусора.
- **Поддержка идемпотентного сброса полей**: Клиенты могут явно стирать опциональные данные пользователя.
- **Централизованная валидация**: Изменение правил поля (например, увеличение максимальной длины `firstName`) в `userFields` автоматически обновляет все зависимые DTO.

### Ограничения и компромиссы:

- При написании запросов Prisma в `apps/api` требуется внимательно указывать проекции через `select` или использовать вспомогательные функции-мапперы для формирования DTO.
