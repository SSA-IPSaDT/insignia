## 📌 Регламент и ограничения по ролям

### 1. Главный разработчик (`@naylour`)

- **Область работы**: Архитектура монорепозитория, инфраструктура (`infra/*`), пакеты (`packages/*`), бэкенд (`apps/api`), фронтенд (`apps/web`), CI/CD и релизы.
- **Ограничения и правила (Guardrails)**:
    - **Контракты данных (`packages/contracts`)**: Запрещено вносить изменения в DTO или сетевые схемы изолированно. Любая правка контракта обязана быть атомарной и одновременно обновлять все зависимые модули (`apps/api`, `apps/web`, `apps/bot`).
    - **Архитектурные сдвиги**: Крупные структурные изменения (добавление пакетов, смена ORM, внедрение брокеров очередей) фиксируются через Architecture Decision Records в `docs/adr/`.

---

### 2. Разработчик сервиса бота (`@segn1s` / `Bot Service Contributor`)

- **Область работы**: Сервис Telegram-бота `apps/bot/` (обработка команд, логика сценариев, интеграция со сторонними Telegram API).
- **Сквозные задачи и изменение контрактов/API (Cross-module Collaboration)**:
    - При разработке функций бота контрибьютор **может** вносить необходимые дополнения в `packages/contracts` (новые схемы, DTO, поля) и связанные эндпоинты в `apps/api`.
    - **Требование целостности**: Если изменяется контракт или API, все проекты обязаны успешно компилироваться и проходить проверки (`bun run check`, `bun run build`).
    - **Согласование через PR**: Изменения оформляются в тематической ветке (например, `feat/bot-notifications`) и вливаются в основную ветку только после обязательного код-ревью и подтверждения тимлидом (`@naylour`).
    - **Инфраструктура и БД**: Для фундаментальных изменений в `infra/*` или моделях `packages/database` рекомендуется предварительно обсудить решение с `@naylour` или оформить предложение через ветку `proposal/...` / `rfc/...`.

## 🤖 Протокол идентификации для AI-агентов

AI-агенты **обязаны** учитывать личность разработчика, с которым ведётся сессия, для предотвращения случайных нарушений зон ответственности:

### Шаг 1: Определение текущего разработчика

Агент считывает имя и email текущего пользователя через команды:

```bash
git config user.name
git config user.email
```

### Шаг 2: Проверка контекста действий

- **Если текущий разработчик — `@naylour`**:
    - При модификации файлов в `packages/contracts`: агент предупреждает:
        > ⚠️ _«Вы изменяете сетевой контракт. Убедитесь, что изменения согласованы и каскадно применены во всех зависимых сервисах (`apps/api`, `apps/web`, `apps/bot`).»_
- **Если текущий разработчик — `@segn1s` (контрибьютор бота)**:
    - При модификации файлов в `packages/contracts` или `apps/api`: агент напоминает:
        > 💡 _«Вы вносите изменения в общий контракт или API под нужды бота. Убедитесь, что все зависимые проекты компилируются без ошибок (`bun run check`), а изменения будут представлены на ревью тимлиду (@naylour) в вашем Pull Request.»_
    - При попытке редактирования файлов фундаментальной инфраструктуры (`infra/*`, `packages/database`): агент предупреждает:
        > ⚠️ _«Внимание: системная инфраструктура и схема базы данных находятся в ведении ведущего разработчика. Согласуйте изменения с @naylour или оформите предложение через ветку proposal/... / rfc/...»_

## 🌿 Регламент именования веток

| Тип задачи                   | Префикс ветки                     | Пример                        | Назначение                                                  |
| :--------------------------- | :-------------------------------- | :---------------------------- | :---------------------------------------------------------- |
| **Фича бота**                | `feat/bot-`                       | `feat/bot-auth-command`       | Работа внутри `apps/bot/`                                   |
| **Багфикс бота**             | `fix/bot-`                        | `fix/bot-timeout-retry`       | Исправление бага в `apps/bot/`                              |
| **Предложение по улучшению** | `rfc/` или `proposal/`            | `rfc/database-telegram-index` | Предложение изменений в общих модулях от контрибьютора бота |
| **Системные / Core задачи**  | `core/`, `infra/`, `api/`, `web/` | `infra/upgrade-bun-1-5`       | Задачи основного мейнтейнера проекта                        |
