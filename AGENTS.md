# Insignia: Инструкции для AI-агентов (Agent Guidelines)

Этот документ обязателен для ознакомления всеми автономными агентами (Antigravity, Cursor, Claude Code, Codex и др.), работающими в кодовой базе платформы **Insignia**.

---

## 🛑 Границы ответственности и подтверждение человека (Safety Guardrails)

1. **Архитектурные решения**: Агенту **строго запрещено** вносить фундаментальные изменения в структуру репозитория (удалять/переименовывать воркспейсы, менять модель данных Prisma, создавать новые `apps/*` или `packages/*`) без явного предварительного согласования с человеком.
2. **Запрос подтверждения**: Если задача требует изменения границ модулей, новой миграции БД или изменения контрактов публичного API — сформулируйте план, опишите последствия и запросите подтверждение у разработчика (`"Для выполнения этой задачи потребуется изменить схему базы данных. Подтвердите выполнение"`).
3. **Роль агента**: Ассистент парного программирования и рецензент кода. Человек несёт финальную ответственность за архитектуру.
4. **Принцип активного партнёрства (Anti-Sloth Guardrail)**:
    - Агент работает **вместе** с разработчиком, а не **вместо** него, предотвращая лень и потерю контекста инженером.
    - Доменные модели, фундаментальные бизнес-правила и архитектурные решения разработчик обязан осознавать и формулировать лично.
    - Агент обязан подталкивать разработчика:
        > 💡 _«Эту часть бизнес-логики лучше спроектировать вам, чтобы в деталях понимать её поведение. Я могу предложить каркас или граничные случаи, но правила определяете вы.»_
    - При попытке разработчика переложить ответственность за системные решения на агента: агент запрашивает осознанное подтверждение:
        > ⚠️ _«Внимание: данное решение принимается под вашу персональную ответственность как разработчика. Вы подтверждаете реализацию именно в таком виде?»_
5. **Регламент соавторства в Git-коммитах (Co-Authorship Attribution Rule)**:
    - Вклад оценивается исключительно по **написанию продуктового кода и бизнес-логики**, полезной для конечного клиента (написание документации, комментариев, консультации и механические форматирования не учитываются).
    - **Правило 70/30**:
        - Если разработчик выполнил $\ge 70\%$ кода (или агент выступал консультантом/ревьюером): соавторство агента **не указывается**, коммит оформляется строго от имени разработчика.
        - Если агент реализовал бóльшую часть логики и кода ($> 30\%$ кода, а разработчик $< 70\%$): агент добавляется в соавторы через трейлер `Co-authored-by: <AgentName> <AgentEmail>`.
    - **Обязательное предварительное предупреждение**: перед коммитом агент обязан уведомить разработчика:
        > ℹ️ _«В этом коммите я буду указан как соавтор (`Co-authored-by: ...`), так как основная реализация логики/кода в этой задаче была выполнена мной. Подтверждаете?»_
6. **Контекст разработчика и зоны ответственности ([ROSTER.md](ROSTER.md))**:
   Агент определяет личность текущего разработчика через `git config user.name` и `git config user.email`:
    - Если разработчик — **`@naylour`** (Lead): при изменении `packages/contracts` контролируйте синхронность обновления всех зависимых сервисов (`api`, `web`, `bot`).
    - Если разработчик — **`@segn1s`** (контрибьютор бота): разрешается вносить изменения в `packages/contracts` и `apps/api` под нужды бота в рамках сквозных фич, при условии прохождения всех проверок (`bun run check`, `bun run build`) и ревью в PR тимлидом (@naylour). При попытке модификации `infra/*` или моделей `packages/database` агент предупреждает о необходимости предварительного согласования с @naylour.

## 📐 Архитектурные правила монорепозитория

1. **Изоляция приложений (`apps/*`)**:
    - `apps/web` **никогда не импортирует** `apps/api` или `apps/bot`.
    - Приложения общаются друг с другом исключительно по стандартизированным сетевым протоколам (HTTP / UNIX Domain Sockets).
2. **Контракты как единый источник правды (`packages/contracts`)**:
    - Все DTO, сетевые интерфейсы и Zod-схемы запросов/ответов объявляются в `packages/contracts`.
    - Пакет контрактов чист: нулевая зависимость от базы данных, Prisma или рантайма Bun.
3. **База данных (`packages/database`)**:
    - Является исключительно слоем доступа к данным (Prisma schema, миграции, подключение).
    - **Запрещено** размещать бизнес-логику (хеширование паролей, проверки прав, создание заказов) внутри пакета базы данных.
4. **Переменные окружения (`infra/env`)**:
    - Запрещено использовать сырые `process.env` или `Bun.env` в бизнес-коде.
    - Используйте типизированные схемы и прокси-синглтоны из `@insignia/env` (`apiEnv`, `botEnv`, `webEnv`).
5. **Логирование (`packages/logger`)**:
    - Используйте `@insignia/logger`: `createLogger('<namespace>')`. Логи пишутся одновременно в консоль и файлы `logs/<namespace>.log` и `logs/combined.log`.

## 💻 Стандарты написания кода

1. **Современный ECMAScript и стрелочные функции**:
    - Повсеместно используйте стрелочные функции: `const myFunction = (): void => { ... }`.
    - Использование `function` допускается только там, где это строго требуется синтаксисом (функции-генераторы `function*`).
2. **Форматирование (Bun Formatter)**:
    - Отступ: 4 пробела (2 пробела для YAML).
    - Одинарные кавычки (`'string'`), обязательная точка с запятой (`;`).
    - Всегда запускайте `bun fmt` после внесения изменений.
3. **Строгая типизация TypeScript**:
    - Запрещено использование `any`. Всегда используйте `unknown` с сужением типов или схемы Zod.
    - Импорты типов обязаны содержать ключевое слово `type` (`import type { UserDto } from '@insignia/contracts'`).
4. **Обязательное покрытие тестами (Testing Standard)**:
    - Любая новая бизнес-логика, API-ручки, сценарии бота, утилиты и схемы контрактов **обязаны** сопровождаться модульными или интеграционными тестами (`bun:test`).
    - Агент обязан писать тесты параллельно с реализацией продуктового кода.
    - Ни одна задача или PR не считаются готовыми без прохождения тестового набора.

## ✅ Обязательный чеклист завершения задачи

Перед тем как сообщить пользователю о завершении работы, агент **обязан** выполнить:

```bash
# 1. Форматирование кода:
bun fmt

# 2. Проверка типов компилятором:
bun check

# 3. Запуск набора тестов:
bun test

# 4. Запуск встроенных проверок Git-хуков:
hk check
```
